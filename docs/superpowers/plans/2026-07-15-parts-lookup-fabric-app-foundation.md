# Parts Lookup Tool — Plan 1: Fabric Data Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the single-source Fabric data layer for the parts cross-branch lookup tool — a new InMaster raw pull with `BinQty` computed in-query — and land it in a newly scaffolded Fabric App's own database, fully validated end to end.

**Architecture:** One new purpose-built ODBC dataflow (`df_InMaster_PartsLookup_Raw`) pulls from `InMaster`, filtered to `VENDOR_CODE IS NOT NULL`, computing `BinQty = ON_HAND_QTY - Pending_Qty`. A generic Fabric Apps (Rayfin) project is scaffolded with a single `PartLocation` entity, deployed to `RP - Fabric Apps Sandbox`. A sync step pushes the raw table into the Fabric App's own SQL Database in Fabric — the exact mechanism (direct SQL write vs. GraphQL mutations) is determined by a discovery task before it's built, since it isn't documented by Microsoft either way.

**Tech Stack:** Fabric Dataflow Gen2, Power Query M, SQL Anywhere ODBC (`dsn=EquipRDB64`), Fabric Apps / Rayfin CLI (`@microsoft/rayfin-core`, `@microsoft/rayfin-client`), TypeScript, SQL Database in Fabric

**This is Plan 1 of 2:**

- **Plan 1 (this plan):** Fabric data foundation — raw table, Fabric App scaffold, sync pipeline
- **Plan 2 (write after Plan 1 ships):** Fabric App frontend — search screen, GraphQL query wiring, styling

**Design spec:** `docs/superpowers/specs/2026-07-15-parts-lookup-fabric-app-design.md`

## Task 2: `InMaster_PartsLookup_Raw` Dataflow

**Files:**

- [ ] **Step 2.1 — Write the query**

Save to `.claude/queries/raw-tables/InMaster_PartsLookup_Raw.pq`:

```
/*
============================================================================
Query: InMaster_PartsLookup_Raw
Dataflow: df_InMaster_PartsLookup_Raw
Location: LH_Master_Data → Dataflows → 01 - Raw Sources
============================================================================

PURPOSE: Single-source cross-branch part lookup data for the Parts Lookup
Tool (Fabric App). Replaces the retired in-store Equip part-lookup utility.
Pulls only parts with a supplier/vendor code present — the exact business
rule for "which branches carry this part through a vendor."

GRAIN: One row per Branch + PartNumber (all franchises, VendorCode not null only)

SOURCE: SQL Anywhere (ODBC: EquipRDB64) — InMaster table

REFRESH: Full refresh. InMaster refreshes in ~3 minutes on average, much
faster than jdis_Part_Information (3x/day) — this table is not capped by
that schedule since it doesn't depend on jdis_Part_Information at all.

BIN QTY: InMaster has no direct bin-quantity column. Computed as
ON_HAND_QTY - Pending_Qty, validated 2026-07-15 at 99.94% exact match
(1,102,498 / 1,103,165 rows) against jdis_Part_Information's independently
tracked BinQty field. Brian has also used this formula for bin qty in
another existing report.

COMMENTS: Sourced from InMaster.NOTE (confirmed 2026-07-15 — not in
jdis_Part_Information, and not the undocumented user_field_1/user_field_2).

DO NOT MODIFY the existing InMaster.pq / InMaster_Raw.pq raw pulls — this
is a separate, purpose-built table for this tool only.
============================================================================
*/

let
    SQL = "
        SELECT
            BRANCH          AS Branch,
            FRANCHISE       AS Franchise,
            PART_NO         AS PartNumber,
            PART_DESC       AS Description,
            BIN_LOCATION    AS Bin,
            SUPER_FROM      AS SuperFrom,
            SUPER_TO        AS SuperTo,
            VENDOR_CODE     AS VendorCode,
            SELL_PRICE1     AS SellPrice1,
            NOTE            AS Comments,
            ON_HAND_QTY     AS OnHandQty,
            Pending_Qty     AS PendingQty
        FROM InMaster
        WHERE VENDOR_CODE IS NOT NULL
    ",

    Source = try Odbc.Query("dsn=EquipRDB64", SQL) otherwise
        error "Failed to connect to InMaster for Parts Lookup Tool. Verify ODBC connection and VENDOR_CODE column.",

    AddBinQty = Table.AddColumn(Source, "BinQty", each [OnHandQty] - [PendingQty], Int64.Type),

    TypedTable = Table.TransformColumnTypes(AddBinQty, {
        {"Branch", type text},
        {"Franchise", type text},
        {"PartNumber", type text},
        {"Description", type text},
        {"Bin", type text},
        {"SuperFrom", type text},
        {"SuperTo", type text},
        {"VendorCode", type text},
        {"SellPrice1", type number},
        {"Comments", type text},
        {"OnHandQty", Int64.Type},
        {"PendingQty", Int64.Type},
        {"BinQty", Int64.Type}
    })
in
    TypedTable
```

```typescript
import {
  entity,
  role,
  uuid,
  text,
  int,
  decimal,
  date,
} from '@microsoft/rayfin-core';

@entity()
@role('authenticated', '*')
export class PartLocation {
  @uuid() id!: string;
  @text() partNumber!: string;
  @text() branch!: string;
  @text() franchise!: string;
  @text() vendorCode!: string;
  @text({ optional: true }) bin?: string;
  @int() binQty!: number;
  @decimal() sellPrice1!: number;
  @text({ optional: true }) superTo?: string;
  @text({ optional: true }) superFrom?: string;
  @text({ optional: true }) comments?: string;
  @date() lastRefreshed!: Date;
}
```

`@role('authenticated', '*')` — every parts staff member with a valid Fabric sign-in gets full read/write access. This is shared reference data, not per-user data, so it deliberately skips the template's default `Todo` pattern of scoping each row to its creating user (`claims.sub.eq(item.userId)`) — that ownership model doesn't apply here.

## Task 5: Build the Sync Step

> **Confirmed by Task 4:** direct SQL path, no GraphQL mutations, no notebook. `id` is database-generated — never mapped or supplied by this dataflow.

**Files:**

- Create: `.claude/queries/facts/PartsLookup_Sync.pq`

- [ ] **Step 5.1 — Write the query**

Save to `.claude/queries/facts/PartsLookup_Sync.pq`:

```
/*
============================================================================
Query: PartsLookup_Sync
Dataflow: df_PartsLookup_Sync
Location: LH_Master_Data → Dataflows → 04 - Fact (or wherever this pipeline stage lives)
============================================================================

PURPOSE: Pushes InMaster_PartsLookup_Raw into the parts-lookup-app Fabric
App's own database (PartLocations table). This is the sync step bridging
the Lakehouse and the Fabric App — the app can't read the Lakehouse
directly, so this dataflow is the only thing that populates it.

SOURCE: References the `InMaster_PartsLookup_Raw` query directly — this
dataflow adds that Lakehouse table as its own individual data source
(not the whole LH_Master_Data lakehouse as a shared connection), so the
query is referenced by name, not via LH_Master_Data{...}[Data] bracket
navigation (that syntax errors with "matches no exports" unless the
whole lakehouse was added as one shared connection instead).

DESTINATION: SQL Server connector, pointed at the SQL Database in Fabric
connection string (from parts-lookup-app's SQL Database child item).
Update method: Replace (full delete + reinsert every run) — matches
InMaster_PartsLookup_Raw being itself a full refresh, and avoids stale
rows lingering for parts that lose their vendor code.

DO NOT map or generate `id` — confirmed 2026-07-15 that the database
auto-generates it on insert; this dataflow's output has no id column
at all, by design.

COLUMN NAMES: renamed here to match PartLocations' camelCase columns
exactly (confirmed via the deployed schema), since Dataflow Gen2's SQL
Server destination maps by name.
============================================================================
*/

let
    Source = InMaster_PartsLookup_Raw,

    AddLastRefreshed = Table.AddColumn(
        Source,
        "lastRefreshed",
        each DateTimeZone.RemoveZone(DateTimeZone.UtcNow()),
        type datetime
    ),

    RenameForApp = Table.RenameColumns(AddLastRefreshed, {
        {"Branch", "branch"},
        {"Franchise", "franchise"},
        {"PartNumber", "partNumber"},
        {"Bin", "bin"},
        {"SuperFrom", "superFrom"},
        {"SuperTo", "superTo"},
        {"VendorCode", "vendorCode"},
        {"SellPrice1", "sellPrice1"},
        {"Comments", "comments"},
        {"BinQty", "binQty"}
    }),

    SelectFinalColumns = Table.SelectColumns(RenameForApp, {
        "partNumber", "branch", "franchise", "vendorCode", "bin",
        "binQty", "sellPrice1", "superTo", "superFrom", "comments", "lastRefreshed"
    })
in
    SelectFinalColumns
```

Note `Description`, `OnHandQty`, and `PendingQty` from `InMaster_PartsLookup_Raw` are deliberately dropped here — they're not part of the `PartLocation` entity (`OnHandQty`/`PendingQty` were only needed upstream to compute `BinQty`).
