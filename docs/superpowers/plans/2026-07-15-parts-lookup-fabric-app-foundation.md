# Parts Lookup Tool — Plan 1: Fabric Data Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the single-source Fabric data layer for the parts cross-branch lookup tool — a new InMaster raw pull with `BinQty` computed in-query — and land it in a newly scaffolded Fabric App's own database, fully validated end to end.

**Architecture:** One new purpose-built ODBC dataflow (`df_InMaster_PartsLookup_Raw`) pulls from `InMaster`, filtered to `VENDOR_CODE IS NOT NULL`, computing `BinQty = ON_HAND_QTY - Pending_Qty`. A generic Fabric Apps (Rayfin) project is scaffolded with a single `PartLocation` entity, deployed to `RP - Fabric Apps Sandbox`. A sync step pushes the raw table into the Fabric App's own SQL Database in Fabric — the exact mechanism (direct SQL write vs. GraphQL mutations) is determined by a discovery task before it's built, since it isn't documented by Microsoft either way.

**Tech Stack:** Fabric Dataflow Gen2, Power Query M, SQL Anywhere ODBC (`dsn=EquipRDB64`), Fabric Apps / Rayfin CLI (`@microsoft/rayfin-core`, `@microsoft/rayfin-client`), TypeScript, SQL Database in Fabric

**This is Plan 1 of 2:**
- **Plan 1 (this plan):** Fabric data foundation — raw table, Fabric App scaffold, sync pipeline
- **Plan 2 (write after Plan 1 ships):** Fabric App frontend — search screen, GraphQL query wiring, styling

**Design spec:** `docs/superpowers/specs/2026-07-15-parts-lookup-fabric-app-design.md`

## Task 2: `InMaster_PartsLookup_Raw` Dataflow

**Files:**
- Create: `.claude/queries/raw-tables/InMaster_PartsLookup_Raw.pq`

- [ ] **Step 2.1 — Write the query**

Save to `.claude/queries/raw-tables/InMaster_PartsLookup_Raw.pq`:

```
/*
============================================================================
Query: InMaster_PartsLookup_Raw
Dataflow: df_InMaster_PartsLookup_Raw
Location: LH_Master_Data → Dataflows → 01 - Raw Sources
============================================================================

PURPOSE: Single-source cross-branch part lookup data for the Parts Lookup
Tool (Fabric App). Replaces the retired in-store Equip part-lookup utility.
Pulls only parts with a supplier/vendor code present — the exact business
rule for "which branches carry this part through a vendor."

GRAIN: One row per Branch + PartNumber (all franchises, VendorCode not null only)

SOURCE: SQL Anywhere (ODBC: EquipRDB64) — InMaster table

REFRESH: Full refresh. InMaster refreshes in ~3 minutes on average, much
faster than jdis_Part_Information (3x/day) — this table is not capped by
that schedule since it doesn't depend on jdis_Part_Information at all.

BIN QTY: InMaster has no direct bin-quantity column. Computed as
ON_HAND_QTY - Pending_Qty, validated 2026-07-15 at 99.94% exact match
(1,102,498 / 1,103,165 rows) against jdis_Part_Information's independently
tracked BinQty field. Brian has also used this formula for bin qty in
another existing report.

COMMENTS: Sourced from InMaster.NOTE (confirmed 2026-07-15 — not in
jdis_Part_Information, and not the undocumented user_field_1/user_field_2).

DO NOT MODIFY the existing InMaster.pq / InMaster_Raw.pq raw pulls — this
is a separate, purpose-built table for this tool only.
============================================================================
*/

let
    SQL = "
        SELECT
            BRANCH          AS Branch,
            FRANCHISE       AS Franchise,
            PART_NO         AS PartNumber,
            PART_DESC       AS Description,
            BIN_LOCATION    AS Bin,
            SUPER_FROM      AS SuperFrom,
            SUPER_TO        AS SuperTo,
            VENDOR_CODE     AS VendorCode,
            SELL_PRICE1     AS SellPrice1,
            NOTE            AS Comments,
            ON_HAND_QTY     AS OnHandQty,
            Pending_Qty     AS PendingQty
        FROM InMaster
        WHERE VENDOR_CODE IS NOT NULL
    ",

    Source = try Odbc.Query("dsn=EquipRDB64", SQL) otherwise
        error "Failed to connect to InMaster for Parts Lookup Tool. Verify ODBC connection and VENDOR_CODE column.",

    AddBinQty = Table.AddColumn(Source, "BinQty", each [OnHandQty] - [PendingQty], Int64.Type),

    TypedTable = Table.TransformColumnTypes(AddBinQty, {
        {"Branch", type text},
        {"Franchise", type text},
        {"PartNumber", type text},
        {"Description", type text},
        {"Bin", type text},
        {"SuperFrom", type text},
        {"SuperTo", type text},
        {"VendorCode", type text},
        {"SellPrice1", type number},
        {"Comments", type text},
        {"OnHandQty", Int64.Type},
        {"PendingQty", Int64.Type},
        {"BinQty", Int64.Type}
    })
in
    TypedTable
```

## Task 5: Build the Sync Step

> Use the path confirmed in Task 4.

- [ ] **Step 5.1A — Direct SQL path (if Task 4 confirmed it)**

Create a Dataflow Gen2 (`df_PartsLookup_Sync`) that:
1. Reads `InMaster_PartsLookup_Raw` from the Lakehouse
2. Connects to the SQL Database in Fabric using the connection string from Step 4.1 as a SQL Server destination
3. On each run: deletes all rows in `part_locations`, then inserts the fresh set (full replace, not incremental upsert — simplest correct approach given `InMaster_PartsLookup_Raw` is itself a full refresh, and avoids stale rows lingering for parts that lose their vendor code)

Add a `lastRefreshed` value (current UTC timestamp) to every row on insert, following the same DST-aware UTC pattern used elsewhere in this repo — see `.claude/queries/DATA-REFRESH-TEMPLATE.pq`.

- [ ] **Step 5.1B — GraphQL mutation path (if Task 4 required it)**

Create a Fabric Notebook (Python) that:
1. Reads `InMaster_PartsLookup_Raw` from the Lakehouse via the SQL Analytics Endpoint
2. Calls a bulk-delete against `part_locations` (or deletes and recreates), then issues create mutations in batches via `RayfinClient` (or direct HTTP POSTs to the app's `/api/graphql` endpoint if the Python notebook can't use the TypeScript client directly)
3. Sets `lastRefreshed` to the current UTC timestamp on every row, same as 5.1A

**Note:** if this path is required, authenticating a headless/scheduled notebook against the deployed app's Fabric-SSO-only auth is a separate open question — Microsoft's docs describe interactive Entra sign-in for the CLI and browser clients, not a documented service-principal/headless flow for the GraphQL API. If you land here, this needs its own quick investigation before Step 5.1B is buildable — don't assume it works without confirming.
